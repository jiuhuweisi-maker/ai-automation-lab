## 目标

在一台内存紧张的 VPS 上部署一套有状态服务链路，同时满足两条硬约束：**不中断机器上已有的服务**、**不让自动更新改变已锁定的版本**。

## 实际步骤（方法层面，来自公开文档）

1. **分三层看待"同一套系统"**：代码层进 Git；配置层（账号、provider/model、票、端口）放仓库外、权限 600；状态层（人设、记忆、日记、收藏）单独打包，明确不进 Git。
2. **先干跑**：`bootstrap.sh --check` 只确认前提齐全、目标目录没被占。
3. **真跑构建**：预检 → 构建固定上游 + 覆盖层 → 装 relay → 生成配置 → 注册控制包 → 离线回归。不碰 QQ 登录、不迁人设、不启动主服务。
4. **逐文件验指纹**：构建产物与线上清单逐个 SHA-256 比对，哈希不对就不继续。
5. **状态单独迁移**：export / import 带 MANIFEST 与 SHA256SUMS；票与凭据不打包。
6. **锁版本与共存**：关自动更新开关；更新器 cron 不安装；同名端口 / 卷 / 单元 / 目录被占就拒绝部署，不停、不覆盖已有服务。
7. **按清单验收**：公开文档列出按顺序检查的多项清单，任一项不对不上线；包括服务状态、登录信息接口返回正常、设置项、真实私信回执、各代废弃语句检查。

## 实际结果

- 可确认的**方法论结论**：代码与配置、状态三层分离；先干跑再真跑；逐文件哈希验收；凭据不进 Git；版本锁定与共存检查；按清单顺序验收。
- 公开事故复盘给出**项目级结论**：一次"不回消息"是本机内存耗尽叠加上游 API 中断，不是登录掉线或鉴权失效；恢复方式是完整备份 + 停用无关服务 + 整机重启，重启前后状态逐一比对。
- 公开文档明确写着：**小内存是硬瓶颈，升配是治本方案**。

## 失败经验（来自公开复盘，可确认的诊断思路）

- **不要反复重启主服务**：内存见底时重启会触发强杀与漫长读盘，反复重启只会更糟。
- **内存见底时不要降低 `swappiness`**：会阻止匿名页换出、诱发 OOM。
- **导出前先设置运行源路径变量**：不设会静默漏掉状态文件。
- **口径更新后旧包必须重打**：否则废弃内容会随下次记忆维护复活。
- **校验清单用二进制方式写回 LF**：Windows 文本模式会转成 CRLF，导致校验全量误报。此坑来自另一个公开复盘 <https://github.com/jiuhuweisi-maker/proxy-tun-loop-postmortem>。
- **不要贸然重做登录**：QQ 冷启动期间接口暂时不可用属正常现象。
- **区分本地故障与上游故障**：要同时看官方状态页和服务日志，不能只看网络连通性。
